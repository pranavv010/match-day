# Production-Readiness Plan: LiveScores (PitchPulse)

## Executive Summary

PitchPulse is a well-architected Android football scores app with solid backend logic (MVVM + Room + Retrofit, 5-layer API guard, multi-key rotation, IST timezone). The core data layer is strong. The two gaps are: **(1) UI sophistication** — the UI is functional but lacks polish, delightful transitions, and a distinctive premium feel; **(2) Overall quality** — missing crash reporting, analytics, tests, accessibility, proper state handling, and release hardening. This plan addresses both across 10 workstreams.

### 1.3 Component Polish

- **AppCard**: Add elevation shadows, tap ripple customization.

- **Files**: `MatchCard.kt`, `LiveBadge.kt`, `DateRibbon.kt`, `AppCard.kt`, `EmptyState.kt`, `BottomNav.kt`

### 1.4 Screen-Level Polish

## Workstream 3: Error Handling & Resilience

### 3.1 Global Error Handler
- **Current**: Errors crash to logcat with `Log.e`; no user-facing crash recovery.
- **Plan**:
  - Add `Thread.setDefaultUncaughtExceptionHandler` in `Application` class (create one) that logs to Firebase Crashlytics and shows a graceful restart.
  - Wrap all `AnimatedContent` in fallback states.
  - Add retry button to all error UI.
- **Files**: New `PitchPulseApplication.kt`, `AndroidManifest.xml`

### 3.2 Network Resilience
- **Current**: Good but no offline indicator. Fails silently, UI shows stale data.
- **Plan**:
  - Add `ConnectivityManager`-based `NetworkObserver` StateFlow.
  - Show persistent "Offline" banner/hit when offline.
  - Retry + exponential backoff for failed fetches (currently only cooldown).
- **Files**: New `core/network/NetworkObserver.kt`, screens integrating `NetworkState` in `MatchUiState`

### 3.3 Room Database Migration Safety
- **Current**: No `Migration` definitions — uses `fallbackToDestructiveMigration()`. **Each app upgrade wipes data.**
- **Plan**: Write explicit migrators migration. Start from version 1 with future-proof schemas (add nullable columns). Destructive migration is fine for pre-launch; lock in a schema before first release.
- **Files**: `LiveScoresDatabase.kt`

### 3.4 API Key Exhaustion UX
- **Current**: When all keys exhausted, rotates silently then returns empty. User sees "No matches".
- **Plan**: Show a small banner when approaching quota (≥70%) — "Data may refresh slower today" — and a dashboard debug visual to swap keys temporarily.
- **Files**: `RetrofitClient.kt`, `FootballRepository.kt`, `MatchUiState.kt`, `HomeScreen.kt`

## Workstream 5: Performance Optimization

### 5.1 Compose Recomposition Auditing
- **Current**: No `LayoutInspector` or composition counts.
- **Plan**:
  - Add `@Stable`/`@Immutable` annotations to model classes (`Match`, `TeamDetails`, `Lineup`).
  - Audit key composables: `MatchCard`, `MatchRow`, `ScoreboardHeaderCard` (re-composed 2-3x/s due to livedata states), `DateRibbon`, `TabRow`.
  - Extract static content from recomposable blocks + `remember`.
- **Files**: All model classes, UI components.

### 5.2 Image Loading
- **Current**: `coil3` with defaults (crossfade, in-memory cache). No disk cache.
- **Plan**: Add `Coil.diskCache(File(...))`—?. Build custom `ImageLoader` with in-memory + disk LRU cache, prefetch queue.
- **Files**: `build.gradle.kts`, new `core/cache/ImageLoaderConfig.kt`

### 5.3 LazyList Performance
- **Current**: All lists use `items()` with new keys. Good, but no stable IDs.
- **Plan**:
  - Ensure stable `key` by data class content equality (already present).
  - For infinite data (dates, matches), use `LazyColumn` + `WindowCorrelation` with `beyondBoundsItems` optimization.
  - Compose profiling to ensure <16ms per frame.

## Workstream 8: Architecture & Tech Debt

### 8.1 Manual DI → Hilt
- **Current**: All ViewModels create their own dependencies in `init {}` or via `viewModel()` factory. No constructor injection. Impossible to test.
- **Plan**: Introduce Hilt. Convert all ViewModels. This is a major refactor but essential for:
  - Testable ViewModels with fake dependencies.
  - Lifecycle-safe scoping.
  - Eliminates direct DB and Retrofit coupling.
- **Files**: `build.gradle.kts`, `MainActivity`, all ViewModels, new `di/` package

### 8.2 Simplify Intertwined HomeScreen State
- **Current**: `MatchUiState.Success` carries 6 fields, some unrelated to the UI.
- **Plan**: Split into composable local state + shared `MatchUiState` with only what Screens need. Use `derivedStateOf` for local grouping.

### 8.3 Splitting MatchesScreen
- **Current**: `MatchesScreen` has its own `LazyColumn` inside a `Column`. Wasteful recomposition.
- **Plan**: Move `MatchList` into its own Composable block; hoist `DateRibbon`.

### 8.4 Rename `LiveScores` → `PitchPulse` consistently
- **Current**: `app_name` is "Live Scores" but theme calls it `LiveScoresTheme`. Firebase project is `pitchpulse-native-app-101`. The readme says PitchPulse. Inconsistent.
- **Plan**: Choose a single brand name.

## Key Architectural Decisions

1. **Hilt over Koin/manual DI**: Hilt is the official solution, has compile-time safety, works seamlessly with AndroidViewModel scope, and enables unit testing immediately.

2. **Keep Manual DI transitional option**: Since Hilt refactor is ~8h, other UI/UX improvements can be done first without changing DI; manual DI works fine for solo devs.

3. **Single Component Refactoring**: Instead of a full rewrite, we'll refactor screens one at a time (Home first, then Matches, then Search, etc.) so the app is always compilable.

4. **Theme Lock**: The PRD mandates dark-theme only + no transparency/glassmorphism. This is non-negotiable per spec — but we can still design a refined dark palette with richer visual hierarchy.

5. **Feature Flags**: Introduce build variant flags for "debug-only" features (like forced live scores, network error tests) to validate UX without deploying fake data.
